# M7 — gérer les versions d'Horizon

Branche : `horizon/m7` (dans `fork/PrismLauncher`), basée sur `horizon/m6`
(M1 + M3 + M4 + M2 + M5 + M6).

Objectif : installer, mettre à jour et supprimer des versions d'Horizon depuis
le fork, sans réimplémenter ce que le launcher officiel fait déjà.

## Pourquoi passer par `horizon-launcher`

Horizon installe ses versions dans
`~/Library/Application Support/horizon-launcher/versions/<tag>/` (macOS) et
chaque dossier contient `horizon-client`, `horizon-prepare`, `horizon-server`,
`horizon-ctl`. Le binaire `horizon-launcher` n'est pas dans ces dossiers : il
vient de l'app Horizon (`Horizon.app/Contents/MacOS/horizon-launcher`) ou du
`PATH` sur Windows/Linux.

M7 ne télécharge donc rien lui-même : il appelle la CLI officielle, qui gère
les releases, les checksums, la sélection et l'élagage.

## Contrat de la CLI (relevé le 2026-11-18)

| Commande | Sortie |
|---|---|
| `horizon-launcher versions --json` | `[{tag, name, date, prerelease, available_here, installed}, …]` |
| `horizon-launcher versions --installed --json` | `{installed: [tag…], selected: tag\|null}` |
| `horizon-launcher update --check --json` | `{horizon: tag\|null, launcher: "0.2.78"\|null, launcher_current: "0.2.68"}` |
| `horizon-launcher install <tag> --json` | `{installed: tag, prepared: bool}` |
| `horizon-launcher remove <tag>` | texte seulement, `--json` ignoré |

Détails qui ont dicté l'implémentation :

- une erreur écrit `error: …` sur stderr et sort en **1** ; le code de sortie
  suffit donc à décider, sans analyser le texte ;
- la progression de `install` n'est écrite que si stderr est un terminal : dans
  un `QProcess`, il n'y a aucun pourcentage. L'interface affiche donc une barre
  indéterminée et le texte de stderr en cas d'échec ;
- `versions` et `update` déclenchent `reuse_prepared_everywhere()` côté
  Horizon : les ressources préparées d'une version sont réutilisées pour les
  autres. C'est le comportement du launcher officiel, pas une surprise du fork ;
- `update` sans `--check` met aussi à jour le launcher lui-même
  (`self_update`), ce qui remplacerait `Horizon.app`. M7 ne l'appelle donc
  jamais : il installe la release choisie avec `install`, et laisse la mise à
  jour du launcher à Horizon.

## Règles de sécurité

- **Aucun accès réseau à l'ouverture** : la boîte liste d'abord ce qui est sur
  le disque (`versions/`), et ne contacte GitHub qu'après « Refresh » ou
  « Check for updates ».
- **Suppression protégée** : une version choisie par le launcher Horizon
  (`selected`), ou épinglée par l'instance (`clientVersion`,
  `preparerVersion`), ne peut pas être supprimée. Confirmation explicite dans
  tous les cas.
- **Pas de sélection cachée** : « Use for this instance » remplit les listes
  déroulantes de la page, et c'est `apply()` qui écrit `horizon.json` — la page
  reste la seule source de vérité.
- **Pas de mise à jour du launcher** : seule la release Horizon est installée.

## Limites connues

- Pas de pourcentage de progression pour `install` (la CLI ne l'écrit pas hors
  terminal) ; l'annulation n'est pas proposée, pour ne pas laisser une version
  à moitié installée.
- `remove` n'a pas de sortie JSON : le fork se fie au code de sortie puis
  relit `versions/`.
- La version installée n'est pas préparée automatiquement : la préparation
  reste l'étape M4, au premier lancement.
