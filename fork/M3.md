## Session

`AuthSession` est converti en JSON compact et écrit sur **stdin**
(`--session-stdin`), jamais dans `argv` :

```json
{"name":"…","uuid":"…","access_token":"…","user_type":"msa"}
```

- `uuid` : sans tirets, en minuscules ; dérivé du nom si absent (compte hors
  ligne).
- `user_type` : `msa` par défaut (contrat validé par le spike M0) ; la valeur
  de `AuthSession` est conservée si elle est renseignée.
- Aucun token n'apparaît dans le log ni dans `ps`.

## Résolution de `horizon-client`

Dans l'ordre :

1. `clientPath` dans `horizon.json` (absolu, ou relatif à l'instance) ;
2. `versions/<clientVersion>/horizon-client` du launcher Horizon
   (`~/Library/Application Support/horizon-launcher` sur macOS,
   `$XDG_DATA_HOME/horizon-launcher` ailleurs, `%APPDATA%` sous Windows) ;
3. la dernière version installée qui contient le binaire ;
4. `horizon-client` dans `PATH`.

## Ligne de commande

```
horizon-client --resources <instance>/horizon/resources \
               --game-dir  <instance>/minecraft \
               --home      <instance>/horizon/home \
               [--width N --height N] \
               [--quickPlaySingleplayer <monde> | --quickPlayMultiplayer <hôte[:port]>] \
               --session-stdin
```

Les dossiers `--home` et `--game-dir` sont créés au besoin. Les logs du jeu
atterrissent dans `<instance>/horizon/home/logs/latest.log`, déjà déclaré
dans `HorizonInstance::getLogFileSearchPaths()`.

## Contrat `--launch-api`

Avant de lancer, l'étape exécute `horizon-client --launch-api` :

- si `launch_api` diffère du pin `horizon.json` (`0.1.0`), un avertissement
  est écrit dans le log (le lancement continue) ;
- le marqueur de crash (`crash_report_line`) est lu depuis la réponse, pas
  recopié en dur ; le chemin du rapport est ajouté au message d'échec.

Codes de sortie traduits : `0` joueur quitté, `1` erreur du jeu, `2` ligne de
commande refusée, `101` panique. Un `Crashed`, `FailedToStart` ou `Aborted`
échoue avec un message explicite. « Kill » dans Prism tue le processus.

## Test effectué

```sh
# 1. préparer les ressources avec le spike M0
cd ~/horizon-prism/spike
python3 horizon_prism_spike.py \
  --instance ~/horizon-prism/fork/testdata/instances/HorizonTest \
  --prism-dir "$HOME/Library/Application Support/PrismLauncher" \
  --resources ~/horizon-prism/fork/testdata/instances/HorizonTest/horizon/resources \
  --home ~/horizon-prism/fork/testdata/instances/HorizonTest/horizon/home \
  --stage prepare --no-complete
# → 98,1 s, 221 Mo

# 2. lancer via Prism
build-horizon/prismlauncher.app/Contents/MacOS/prismlauncher \
  -d "$PWD/testdata" -l HorizonTest -o TestPlayer --alive
```

## Ce que M3 ne fait pas

- pas de préparation/repair automatique (M4) : si
  `horizon/resources/assets/` manque, « Play » échoue toujours avec le
  message « not prepared » ;
- pas de `--player-dir` par compte (les options/screenshots restent dans le
  game dir Prism) ;
- pas de gestion de `--fullscreen` ni de « maximisé » ;
- pas de scan de mods Horizon, pas de page de réglages (M2/M5) ;
- pas de vérification complète `horizon-prepare --check` (M4).
