## Modèle

`HorizonMod` décrit un mod trouvé dans le dossier de jeu :

| Champ | Sens |
|---|---|
| `id`, `name`, `version`, `description` | manifeste |
| `kind` | `Content`, `Native` ou `Both` (un `.hmod` qui porte les deux) |
| `folder` | mod-dossier, celui que `--dev-mod` accepte |
| `api`, `side` | mod de contenu : `0.1`/`0.2`/`0.3`, `client`/`server`/`both` |
| `game`, `horizonCommit`, `mixinsCommit`, `hooks` | mod natif |
| `problem` | raison de ne pas pouvoir tourner, vide sinon |

`HorizonMods::scan(gameRoot)` lit deux dossiers :

- `<game>/horizon-mods` : `.hmod`, dossiers avec `horizon-mod.toml` (ou
  `horizon-native.json`) ;
- `<game>/horizon-native-mods` : `.hnmod` et `.hmod`, dossiers avec
  `horizon-native.json`.

Un `.hmod` peut être un mod de contenu, un mod natif, ou les deux. Un `.jar`
est listé avec le problème « Java mods do not run on Horizon » plutôt que
d'être ignoré silencieusement. Les manifestes sont lus dans le zip avec
`MMCZip::ArchiveReader` et validés (`id` `[a-z0-9_]{1,64}`, révisions de
40 hex, `schema = 1`, `registries` pour l'API 0.2, ids identiques quand les
deux manifestes sont présents).

## `horizon-mods.txt`

Le fichier est la seule source de vérité pour l'état activé/désactivé, avec
exactement les règles du jeu (`horizon-client-render/src/mod_list.rs`) :

- mod de contenu : éteint tant qu'il n'y a pas de ligne `mod.<id>:true` ;
- mod natif : allumé tant qu'il n'y a pas de ligne `mod.<id>:false` ;
- les lignes `key.<id>.<name>:<touche>` (raccourcis choisis par le joueur)
  sont conservées telles quelles.

`HorizonModList` parse, sérialise et écrit ce fichier ; l'écriture est
déterministe (mods triés, puis clés) et n'a lieu que si la liste est non vide
ou si le fichier existe déjà, comme le fait le jeu.

## Page « Horizon Mods »

Tableau : activé, nom, id, version, type, état. Boutons : **Add…**,
**Remove**, **Refresh**, **Open folder**.

- la case à cocher écrit immédiatement `horizon-mods.txt` ;
- les entrées illisibles ou invalides n'ont pas de case et affichent leur
  problème dans la colonne « Status » ;
- **Add…** copie les fichiers choisis dans le bon dossier (`.hnmod` →
  `horizon-native-mods`, sinon `horizon-mods`) et renomme en `nom-1.ext` en
  cas de collision ;
- **Remove** supprime le fichier ou le dossier après confirmation.

Les pages de mods Java de Prism (`ModFolderPage`, `CoreModFolderPage`,
`NilModFolderPage`) sont masquées pour les instances Horizon : leurs
dossiers ne sont jamais lus par `horizon-client`.

## Limite assumée : les mods natifs

Ce fork lance un `horizon-client` précompilé. Les `.hnmod` sont donc listés,
activables et supprimables, mais **ils ne sont pas compilés dans le jeu** :
la page affiche « installed, not built into this game » au lieu de laisser
croire qu'ils tournent. Compiler des mods natifs demanderait toute la chaîne
Rust de Horizon, ce qui est hors du périmètre de ce fork.

## Tests

`tests/HorizonMod_test.cpp` (QtTest, sans GUI) :

- parse/sérialisation de `horizon-mods.txt`, y compris les lignes `key.*` ;
- contenu éteint par défaut, natif allumé par défaut ;
- scan de `.hmod`, `.hnmod`, mod-dossier et fichier invalide ;
- `.hmod` combiné avec des ids différents → problème signalé ;
- aller-retour sur disque, et pas de fichier vide créé.

```sh
cmake -S PrismLauncher -B build-horizon -DBUILD_TESTING=ON
cmake --build build-horizon --target LauncherTests
./build-horizon/LauncherTests HorizonMod_test
```

## Écarts par rapport au plan initial

- pas d'index Horizon ni de téléchargement : le plan prévoyait
  `modplatform/ModIndex.h`, mais il n'existe pas encore de registre public
  interrogeable depuis un client tiers ; M5 se limite au contenu local ;
- pas de mise à jour automatique des mods (le launcher officiel compare des
  versions dans son registre) ;
- pas de vérification de signature : elle appartient au registre Horizon, pas
  au fichier.
