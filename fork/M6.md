# M6 — packaging du fork

Branche : `horizon/m6` (dans `fork/PrismLauncher`), basée sur `horizon/latest`
(M1 + M3 + M4 + M2 + M5).

Objectif : produire un launcher qui porte son propre nom, son propre bundle id
et son propre dossier de données, pour cohabiter avec Prism, et préparer la
distribution (updater, signature, CI).

## L'option `HORIZON_FORK`

Tout est derrière une option CMake, désactivée par défaut : la construction
Prism d'origine reste inchangée.

```sh
cmake -S PrismLauncher -B build-fork -DHORIZON_FORK=ON ...
# ou
fork/build-m6.sh
```

| Réglage | Prism | Fork (`HORIZON_FORK=ON`) |
|---|---|---|
| Cible / app | `PrismLauncher` / `prismlauncher.app` | `HorizonPrismLauncher` / `horizon-prism.app` |
| Binaire | `prismlauncher` | `horizon-prism` |
| Bundle id (macOS) | `org.prismlauncher.PrismLauncher` | `dev.playhorizon.HorizonPrismLauncher` |
| Nom affiché | Prism Launcher | Horizon Prism Launcher |
| Dossier de données | `~/Library/Application Support/PrismLauncher` | `~/Library/Application Support/HorizonPrismLauncher` |
| Variable `*_DATA_DIR` | `PRISMLAUNCHER_DATA_DIR` | `HORIZONPRISMLAUNCHER_DATA_DIR` |
| Fichier de config | `prismlauncher.cfg` | `horizon-prism.cfg` |
| Domaine | `prismlauncher.org` | `playhorizon.dev` |
| Dépôt Git (à-propos) | PrismLauncher/PrismLauncher | LuBart08/horizon-prism-launcher |
| Updater GitHub | Prism | LuBart08/horizon-prism-launcher (Windows/Linux) |
| Sparkle (macOS) | clé + appcast Prism | désactivé |

Le nom interne (`Launcher_CommonName`) sert à `QStandardPaths` : c'est lui qui
sépare réellement les données. Les deux launchers peuvent donc être installés
côte à côte sans mélanger instances et réglages.

La variable de redirection est dérivée du même nom
(`BuildConfig.LAUNCHER_NAME.toUpper()` + `_DATA_DIR`), d'où
`HORIZONPRISMLAUNCHER_DATA_DIR` sans tiret ni underscore interne.

## Ce qui change

| Fichier | Changement |
|---|---|
| `CMakeLists.txt` | option `HORIZON_FORK`, nom du binaire, updater, Sparkle |
| `program_info/CMakeLists.txt` | noms installés (app id, binaire, copyright, user-agent) |
| `program_info/*.in` | inchangés : les entrées restent les fichiers Prism |
| `.github/workflows/horizon.yml` | build + tests macOS/Linux/Windows |
| `fork/build-m1.sh` | accepte `HORIZON_FORK`, `BUILD_TESTING`, `TARGET` |
| `fork/build-m6.sh` | nouveau : build brandé + tests |

Les fichiers d'art (icônes, SVG, `.desktop`, métadonnées) restent ceux de
Prism : seule leur **destination** est renommée. C'est volontaire tant que le
fork n'a pas d'identité visuelle propre, et la licence GPL-3.0 de Prism est
conservée (voir `LICENSE` et `HORIZON.md`).

## Updater

- **Windows / Linux** : `Launcher_UPDATER_GITHUB_REPO` pointe vers le dépôt du
  fork, et `Launcher_BUILD_ARTIFACT` vaut `windows-x86_64` ou `linux-x86_64`.
  L'updater existant interroge `api.github.com/repos/<owner>/<repo>/releases`
  et choisit l'asset dont le nom contient la plateforme, l'architecture et,
  pour Windows, le type d'installeur. Les releases du fork doivent donc
  contenir des assets nommés avec ces chaînes (par exemple
  `horizon-prism-12.0.0-windows-x86_64-Setup.exe`,
  `horizon-prism-12.0.0-linux-x86_64.tar.gz`).
- **macOS** : Prism utilise Sparkle, pas l'updater GitHub. Sans clé Ed25519
  propre au fork, laisser la clé et l'appcast de Prism ferait proposer les
  versions Prism et pourrait remplacer le fork. Les deux variables sont donc
  vidées et les mises à jour sont désactivées sur macOS jusqu'à ce que le fork
  publie son propre appcast.

## Signature et distribution

Les artefacts produits ici sont **non signés**. Les secrets ne peuvent pas
être générés par le dépôt ; voici ce qu'il faut fournir.

### macOS

1. Certificat **Developer ID Application** exporté en `.p12`
   (`APPLE_CODESIGN_CERT` + `APPLE_CODESIGN_PASSWORD`) et son identité
   (`APPLE_CODESIGN_ID`).
2. Signature avec le hardened runtime et les entitlements du dépôt :

   ```sh
   codesign --deep --force --options runtime --timestamp \
     --entitlements program_info/App.entitlements \
     --sign "$APPLE_CODESIGN_ID" horizon-prism.app
   ```

3. Notarisation (`APPLE_NOTARIZE_APPLE_ID`, `APPLE_NOTARIZE_TEAM_ID`,
   `APPLE_NOTARIZE_PASSWORD`) puis `xcrun stapler staple`.
4. Pour des mises à jour Sparkle : générer une paire de clés
   (`generate_keys`), publier la clé publique dans
   `MACOSX_SPARKLE_UPDATE_PUBLIC_KEY`, héberger un `appcast.xml` et remplir
   `MACOSX_SPARKLE_UPDATE_FEED_URL`, puis signer les archives avec
   `sign_update`.

### Windows

- Azure Trusted Signing (`AZURE_CLIENT_ID`, `AZURE_TENANT_ID`,
  `AZURE_SUBSCRIPTION_ID`) ou un certificat Authenticode classique avec
  `signtool sign /fd SHA256 /tr <timestamp> /td SHA256`.
- L'installeur NSIS généré par `program_info/win_install.nsi.in` doit être
  signé, ainsi que `horizon-prism.exe` et `horizon-prism_updater.exe`.

### Linux

- Facultatif : signature GPG détachée des archives (`GPG_PRIVATE_KEY`,
  `GPG_PRIVATE_KEY_ID`) comme le fait le workflow Prism.

## CI

`.github/workflows/horizon.yml` construit le fork avec `HORIZON_FORK=ON` sur
macOS (build universel `x86_64;arm64`), Ubuntu 24.04 et Windows 2022 (MSVC),
lance `ctest` puis publie un bundle macOS comme artefact de workflow. Il
réutilise l'action locale `setup-dependencies` de Prism (Qt, vcpkg, ccache).

Le workflow tourne sur `horizon/latest` et sur chaque branche `horizon/mN`.
Les trois jobs configurent, compilent et passent les 25 tests (dont
`HorizonMod_test` et `HorizonRelease_test`).

L'artefact macOS, `HorizonPrismLauncher-macOS-unsigned.zip`, est un build
**Debug** :

- produit par `cmake --install` : Prism ne déploie Qt (frameworks, plugins,
  icône, jars) qu'à l'installation, pas dans l'arbre de build ;
- signé **ad hoc** (`codesign --sign -`) pour éviter le message « endommagé »
  sur Apple silicon, mais ni Developer ID ni notarisation ;
- contrôlé par le workflow : `QtCore.framework`, icône, bundle id
  `dev.playhorizon.HorizonPrismLauncher`, puis vérification de la signature.

Trois pièges rencontrés en mettant le workflow au point, corrigés depuis :

- sous Windows, le shell par défaut (PowerShell) n'étend pas `$CMAKE_PRESET` :
  le preset était silencieusement perdu et vcpkg absent. Le job force
  `shell: bash`, comme le workflow Prism ;
- le preset `default` est Ninja Multi-Config : le binaire est dans
  `build/$BUILD_TYPE/`, et un bundle vide existe aussi à la racine de `build/`.
  Chercher le premier dossier `*.app` produisait une archive de 1,7 Ko ;
- les images arm64 (`macos-26`, puis `macos-15`) ont refusé plusieurs fois de
  fournir un runner (« not acquired after multiple attempts », contraintes de
  capacité). Le job utilise donc `macos-15-intel` : le runner est attribué
  immédiatement et le build reste universel (`x86_64;arm64`). Contrepartie :
  sans cache vcpkg compatible, la première exécution recompile les dépendances
  et dure beaucoup plus longtemps.

Détails utiles :

- CMake nomme le bundle d'après `OUTPUT_NAME`, donc l'app s'appelle
  `horizon-prism.app` (et non `HorizonPrismLauncher.app`). Les destinations
  d'installation (`Contents/MacOS`, `Contents/Resources`, `Contents/Frameworks`)
  ont été alignées sur ce nom ; sans ça l'icône partait dans un second bundle
  vide. Le nom affiché, le bundle id et le `.icns` restent, eux, « Horizon
  Prism Launcher ».
- `main.cpp` appelle `Q_INIT_RESOURCE(prismlauncher)` : le `.qrc` généré garde
  donc le nom `prismlauncher.qrc` même quand le binaire est renommé.
- `QStandardPaths` sur macOS suit `NSHomeDirectory()`, pas `$HOME` : un `HOME`
  temporaire ne déplace pas le dossier de données. La redirection se fait par
  `HORIZONPRISMLAUNCHER_DATA_DIR` (vérifié), et la séparation par défaut a été
  constatée sur le vrai dossier, Prism intact.
- L'installation complète exige `NewLaunch.jar` / `NewLaunchLegacy.jar`, dont le
  build Java utilise `-source 7`, refusé par le JDK 25 présent ici (il faut un
  JDK ≤ 19, comme le `JAVA_HOME` JDK 17 des workflows Prism). Le binaire et les
  ressources s'installent quand même ; c'est une limite de l'outillage local,
  pas du fork.

Non testé : signature et notarisation Apple, signature Windows, mises à jour
Sparkle (clés absentes). L'artefact macOS de la CI est un build **Debug** non
signé : il sert aux essais, pas à la distribution.
