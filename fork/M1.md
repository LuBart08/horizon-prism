# M1 — squelette du fork Prism pour Horizon

Branche : `horizon/m1` (dans `fork/PrismLauncher`), basée sur
`PrismLauncher/develop` @ `1a6438d`.

Objectif : Prism sait charger une instance **Horizon** et refuse de la lancer
proprement. Aucun moteur Horizon n'est réimplémenté : M1 ne fait que brancher
le modèle d'instance et couper le chemin Java.

> ✅ **Compilé et testé** le 16/11/2026 sur macOS 26.7.2 (x86_64) avec
> Qt 6.8.3. Voir « Compilation et test » plus bas.

## Ce qui change

| Fichier | Changement |
|---|---|
| `launcher/minecraft/HorizonInstance.h` | nouveau : sous-classe de `MinecraftInstance` |

## Pourquoi ces overrides

`MinecraftInstance` est réutilisé pour le game dir, les sauvegardes, les
captures, le compte Microsoft et l'UI de lancement. Mais il suppose un
`mmc-pack.json` et une JVM. `HorizonInstance` neutralise ces hypothèses :

| Méthode | Raison |
|---|---|
| `loadSpecificSettings()` | `MinecraftInstance` réécrit `InstanceType` en `OneSix` ; on restaure `Horizon` après l'appel, sinon l'instance redevient une instance Java au redémarrage |
| `saveNow()` | sauvegarde `horizon.json` en plus de `instance.cfg` |
| `traits()` | pas de `PackProfile` à interroger : renvoie `{"Horizon"}` |
| `createUpdateTask()` | aucun téléchargement Java ; la préparation arrive en M4 |
| `createLaunchTask()` | n'exécute aucune étape Java ; ajoute `HorizonNotPrepared` |
| `getStatusbarDescription()` | « Horizon <version> (stable) not prepared » |
| `verboseDescription()` | décrit version, pins et état de préparation dans le log |
| `instanceConfigFolder()` | `horizon/config` (le jeu n'est pas Java) |
| `getLogFileSearchPaths()` | `horizon/home/logs` d'abord |
| `canExport()` | l'export de pack Prism n'a pas de sens ici |

### Modèle `horizon.json`

Créé au premier `saveNow()`, lu au chargement. Valeurs par défaut alignées
sur le nightly 2026-11-13 :

```json
{
  "formatVersion": 1,
  "channel": "stable",
  "minecraft": "26.3",
  "clientVersion": "",
  "preparerVersion": "",
  "pins": { "launch_api": "0.1.0", "output_version": 4, "native_hooks_api": 415 }
}
```

`clientVersion` et `preparerVersion` doivent rester identiques : un
`output_version` différent rend les ressources « périmées ».

### Dossiers

```
<instance>/
├── instance.cfg          InstanceType=Horizon
├── horizon.json          modèle Horizon (source de vérité)
├── horizon/
│   ├── resources/        horizon-client --resources
│   ├── home/             horizon-client --home (logs, crash-reports)
│   ├── root/             horizon-prepare --root
│   └── config/           instanceConfigFolder()
└── minecraft/            game dir Prism (saves, screenshots, options)
```

## Créer une instance de test à la main

La création depuis « New Instance » n'est pas encore branchée (M2/M5).
Le script `fork/make-test-instance.sh` crée une instance jetable :

```sh
cd ~/horizon-prism/fork
./make-test-instance.sh            # crée fork/testdata/instances/HorizonTest
```

Équivalent manuel :

```sh
PRISM="$HOME/Library/Application Support/PrismLauncher"
INST="$PRISM/instances/HorizonTest"
mkdir -p "$INST/horizon/resources" "$INST/horizon/home" "$INST/horizon/root"
cat > "$INST/instance.cfg" <<'EOF'
InstanceType=Horizon
name=Horizon Test
iconKey=default
EOF
cat > "$INST/horizon.json" <<'EOF'
{
  "formatVersion": 1,
  "channel": "stable",
  "minecraft": "26.3",
  "clientVersion": "nightly-2026-11-13-9f42064",
  "preparerVersion": "nightly-2026-11-13-9f42064",
  "pins": { "launch_api": "0.1.0", "output_version": 4, "native_hooks_api": 415 }
}
EOF
```

Puis démarrer Prism : l'instance doit apparaître, s'ouvrir, et « Play » doit
échouer avec :

```
Horizon resources are not prepared yet: …/horizon/resources
This Horizon instance has no prepared resources yet. Automatic preparation arrives in milestone M4.
```

et `instance.cfg` doit conserver `InstanceType=Horizon` après redémarrage.

Pour aller plus loin sans M3, les ressources réelles peuvent être préparées
avec le spike M0 :

```sh
cd ~/horizon-prism/spike
python3 horizon_prism_spike.py --instance HorizonTest --stage prepare --no-complete
```

`Play` affichera alors « launching arrives in milestone M3 ».

## Compilation et test (16/11/2026)

### Résultat

- configuration CMake + build Ninja : **427/427 unités compilées**, y compris
  `HorizonInstance.cpp` et `HorizonNotPrepared.cpp` ;
- binaire produit :
  `fork/build-horizon/prismlauncher.app/Contents/MacOS/prismlauncher`
  (x86_64, Debug) ;
- aucun changement nécessaire au code M1 pour compiler.

Commande utilisée :

```sh
cd ~/horizon-prism/fork
./build-m1.sh
```

### Outillage sans administrateur

Cette machine n'a pas Homebrew et `sudo` exige un mot de passe. Tout
l'outillage est donc en espace utilisateur :

| Outil | Installation |
|---|---|
| Qt 6.8.3 (universel) | `aqt install-qt mac desktop 6.8.3 clang_64 --modules qtnetworkauth qtimageformats qtshadertools -O ~/Qt` |
| CMake 4.4.5, Ninja | `python3 -m pip install --user cmake ninja`, liés dans `~/.local/bin` |
| pkg-config 3.0.11 | compilé depuis `pkgconf` dans `~/.local` |
| cmark, libarchive, libqrencode, toml++, zlib | `cmake/vcpkg/vcpkg install --triplet x64-osx` |

`build-m1.sh` fixe `CMAKE_PREFIX_PATH` vers `~/Qt/6.8.3/macos`, utilise le
toolchain vcpkg du dépôt, `x64-osx`, `ENABLE_LTO=OFF`, `BUILD_TESTING=OFF`.

### Problème AGL (SDK macOS 26)

Qt 6.8 `FindWrapOpenGL.cmake` ajoute `-framework AGL` (via
`find_library(WrapOpenGL_AGL NAMES AGL)`). Le SDK macOS 26 ne fournit plus
`AGL.framework`, alors que `/System/Library/Frameworks/AGL.framework` existe
encore : CMake mémorise ce chemin dans le cache mais `ld` ne le trouve pas.

Solution : `build-m1.sh` génère un framework factice vide dans
`fork/stubs/AGL.framework` (aucun symbole AGL n'est utilisé par Prism),
injecté via :

```
-DCMAKE_LIBRARY_PATH="$ROOT/stubs" -U WrapOpenGL_AGL
```

Le `-U` est nécessaire : sans lui, un cache CMake existant conserve
`/System/Library/Frameworks/AGL.framework` et le lien échoue toujours.
Le stub ne sert qu'à l'édition de liens ; il n'est pas embarqué dans l'app.
Il est régénéré à la demande et n'est pas versionné (`fork/stubs/` est ignoré).

### Test de chargement et de lancement

```sh
cd ~/horizon-prism/fork
./make-test-instance.sh
build-horizon/prismlauncher.app/Contents/MacOS/prismlauncher \
    -d "$PWD/testdata" -l HorizonTest -o TestPlayer --alive
```

Observé dans le log :

```
Info: Found instance ID "HorizonTest" …
Debug: Loaded instance "Horizon Test" from "…/HorizonTest"
Debug: <> Instance "HorizonTest" launching
Warning: Horizon resources are not prepared yet: "…/HorizonTest/horizon/resources"
```

et `instance.cfg` contient toujours `InstanceType=Horizon` après le
chargement (la réécriture en `OneSix` par `MinecraftInstance` est bien
annulée).

Avec `horizon/resources/assets/` présent, le message devient :

```
Horizon launching is not wired into the launcher yet (milestone M3).
```

Les deux branches de `HorizonNotPrepared` sont donc validées.

> ⚠️ **Porte « compte Microsoft »** : même avec `-o`, Prism exige un compte
> MSA propriétaire de Minecraft avant de créer la tâche de lancement
> (`LaunchController::decideAccount`/`decideLaunchMode`). Un compte hors-ligne
> déclenche l'assistant de connexion, un faux compte MSA déclenche un dialogue
> de réauthentification. Pour atteindre `HorizonNotPrepared`, le test a utilisé
> un **patch local temporaire** de `LaunchController` (contournement pour
> `InstanceType=Horizon`), retiré ensuite : le code M1 commité est inchangé.
> M3 devra décider comment les instances Horizon s'authentifient (session
> Microsoft transmise à `horizon-client`, ou mode hors-ligne assumé).

> ℹ️ Au lancement, Prism journalise
> `Components file …/mmc-pack.json doesn't exist. This should never happen.`
> C'est un avertissement sans effet (le profil n'est pas utilisé par Horizon) ;
> M2/M5 pourront fournir un `mmc-pack.json` minimal ou un profil dédié.

## Prérequis de compilation (générique)

- **Qt 6.8+** (Core, Widgets, Network, NetworkAuth, Concurrent, Gui, Xml, Test,
  CoreTools, OpenGL) ;
- **CMake ≥ 3.25** et **Ninja** ;
- un compilateur C++20 ;
- les sous-modules Prism (`git submodule update --init --recursive`) ;
- les dépendances vcpkg du manifeste Prism.

Sur une machine avec Homebrew, l'équivalent est :

```sh
cd fork/PrismLauncher
git submodule update --init --recursive
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug \
      -DCMAKE_PREFIX_PATH="$(brew --prefix qt)" \
      -DCMAKE_TOOLCHAIN_FILE=cmake/vcpkg/scripts/buildsystems/vcpkg.cmake
cmake --build build --target PrismLauncher
```

## Ce que M1 ne fait pas

- aucun lancement réel (`HorizonNotPrepared` échoue volontairement) ;
- aucune préparation/repair (M4) ;
- aucune page de réglages Horizon (M2) — l'onglet « Version » de Prism
  s'affiche encore et signale l'absence de `mmc-pack.json` ;
- aucune création via l'UI ;
- aucune gestion de session Horizon (M3).
