# M1 — squelette du fork Prism pour Horizon

Branche : `horizon/m1` (dans `fork/PrismLauncher`), basée sur
`PrismLauncher/develop` @ `1a6438d`.

Objectif : Prism sait charger une instance **Horizon** et refuse de la lancer
proprement. Aucun moteur Horizon n'est réimplémenté : M1 ne fait que brancher
le modèle d'instance et couper le chemin Java.

> ⚠️ **Ce code n'a pas encore été compilé** : cette machine n'a ni Qt 6, ni
> CMake, ni Ninja (voir « Compiler » plus bas). La revue a été faite contre
> les en-têtes réels de Prism.

## Pourquoi ces overrides

`MinecraftInstance` est réutilisé pour le game dir, les sauvegardes, les
captures, le compte Microsoft et l'UI de lancement. Mais il suppose un
`mmc-pack.json` et une JVM. `HorizonInstance` neutralise ces hypothèses :

| Méthode | Raison |
|---|---|
| `loadSpecificSettings()` | `MinecraftInstance` réécrit `InstanceType` en `OneSix` ; on restaure `Horizon` après l'appel, sinon l'instance redevient une instance Java au redémarrage |
| `saveNow()` | sauvegarde `horizon.json` en plus de `instance.cfg` |
| `traits()` | pas de `PackProfile` à interroger : renvoie `{"Horizon"}` |
| `createUpdateTask()` | aucun téléchargement Java ; la préparation arrive en M4 |
| `createLaunchTask()` | n'exécute aucune étape Java ; ajoute `HorizonNotPrepared` |
| `getStatusbarDescription()` | « Horizon <version> (stable) not prepared » |
| `verboseDescription()` | décrit version, pins et état de préparation dans le log |
| `instanceConfigFolder()` | `horizon/config` (le jeu n'est pas Java) |
| `getLogFileSearchPaths()` | `horizon/home/logs` d'abord |
| `canExport()` | l'export de pack Prism n'a pas de sens ici |

### Modèle `horizon.json`

Créé au premier `saveNow()`, lu au chargement. Valeurs par défaut alignées
sur le nightly 2026-11-13 :

```json
{
  "formatVersion": 1,
  "channel": "stable",
  "minecraft": "26.3",
  "clientVersion": "",
  "preparerVersion": "",
  "pins": { "launch_api": "0.1.0", "output_version": 4, "native_hooks_api": 415 }
}
```

`clientVersion` et `preparerVersion` doivent rester identiques : un
`output_version` différent rend les ressources « périmées ».

### Dossiers

```
<instance>/
├── instance.cfg          InstanceType=Horizon
├── horizon.json          modèle Horizon (source de vérité)
├── horizon/
│   ├── resources/        horizon-client --resources
│   ├── home/             horizon-client --home (logs, crash-reports)
│   ├── root/             horizon-prepare --root
│   └── config/           instanceConfigFolder()
└── minecraft/            game dir Prism (saves, screenshots, options)
```

## Créer une instance de test à la main

La création depuis « New Instance » n'est pas encore branchée (M2/M5).

```sh
PRISM="$HOME/Library/Application Support/PrismLauncher"
INST="$PRISM/instances/HorizonTest"
mkdir -p "$INST/horizon/resources" "$INST/horizon/home" "$INST/horizon/root"
cat > "$INST/instance.cfg" <<'EOF'
InstanceType=Horizon
name=Horizon Test
iconKey=default
EOF
cat > "$INST/horizon.json" <<'EOF'
{
  "formatVersion": 1,
  "channel": "stable",
  "minecraft": "26.3",
  "clientVersion": "nightly-2026-11-13-9f42064",
  "preparerVersion": "nightly-2026-11-13-9f42064",
  "pins": { "launch_api": "0.1.0", "output_version": 4, "native_hooks_api": 415 }
}
EOF
```

Puis démarrer Prism : l'instance doit apparaître, s'ouvrir, et « Play » doit
échouer avec :

```
Horizon resources are not prepared yet: …/horizon/resources
This Horizon instance has no prepared resources yet. Automatic preparation arrives in milestone M4.
```

et `instance.cfg` doit conserver `InstanceType=Horizon` après redémarrage.

Pour aller plus loin sans M3, les ressources réelles peuvent être préparées
avec le spike M0 :

```sh
cd ~/horizon-prism/spike
python3 horizon_prism_spike.py --instance HorizonTest --stage prepare --no-complete
```

`Play` affichera alors « launching arrives in milestone M3 ».

## Compiler

Prérequis Prism (voir `README.md` du dépôt Prism) :

- **Qt 6.5+** (Core, Widgets, Network, Concurrent, Gui, Xml, Test) ;
- **CMake ≥ 3.24** et **Ninja** ;
- un compilateur C++20 (Apple clang 21 convient) ;
- les sous-modules Prism (`git submodule update --init --recursive`) ;
- sur macOS : `brew install qt cmake ninja` puis
  `cmake --preset macos-dev` (ou `-DCMAKE_PREFIX_PATH="$(brew --prefix qt)"`).

Cette machine n'a **ni Homebrew, ni Qt, ni CMake, ni Ninja** : le build doit
se faire sur une autre machine ou après installation. Commandes :

```sh
cd fork/PrismLauncher
git submodule update --init --recursive
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug \
      -DCMAKE_PREFIX_PATH="$(brew --prefix qt)"
cmake --build build --target PrismLauncher
```

## Ce que M1 ne fait pas

- aucun lancement réel (`HorizonNotPrepared` échoue volontairement) ;
- aucune préparation/repair (M4) ;
- aucune page de réglages Horizon (M2) — l'onglet « Version » de Prism
  s'affiche encore et signale l'absence de `mmc-pack.json` ;
- aucune création via l'UI ;
- aucun test automatisé (pas de build).
